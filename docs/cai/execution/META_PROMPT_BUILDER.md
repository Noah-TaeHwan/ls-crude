# 메타프롬프트 — 새로운 요구를 작은 실행 패킷으로 바꾸기

기획 변경 또는 새 작업이 생겼을 때만 사용한다. 매 작업마다 기존 카드를 재생성하지 않는다. 아래 출력은 작업 방법 제안이며 승인·실행·완료 기록이 아니다.

```text
역할: CAI의 제품 기획을 “새로운 동료가 추측 없이 수행할 수 있는 작업 명세”로 변환한다.
실행자는 범용 보급형 모델일 수 있다. 암묵적 맥락, 자유로운 재설계, 다중 파일 병렬 작업에 기대지 마.

입력:
- 사용자 요청과 승인된 범위
- 현행 기획서/AGENTS/원장/관련 실제 소스
- 관련 인터페이스·테스트 방식·도구 가용성
이 중 필요한 입력이 없으면 조회부터 한다. 확인 불가능한 사실을 만들어 채우지 않는다.

변환 절차:
1. 요청을 관측 가능한 수용 조건으로 바꾼다. 각 조건에 기획 절/사용자 문장을 연결한다.
2. 같은 테스트로 확인할 수 있는 하나의 변경 단위만 고른다.
   파일이 너무 많거나 서로 다른 승인/실패 원인이 있으면 의존성이 있는 카드들로 나눈다.
3. 이미 결정된 제품/통계/보안 정책은 그대로 사용한다. 미결정은 승인 필요 항목으로 분리한다.
4. 입력·출력 타입과 기존 심벌을 소스에서 확인하고 한 가지 인터페이스만 명시한다.
5. 경계 사례를 정상/없음/오류/권한/구주소로 나누어 기대 행동을 정확히 적는다.
6. 실제 테스트 명령 또는 기존 테스트 스타일의 실행 가능한 검증을 지정한다.
   실행 도구가 없으면 NOT_RUN과 다음 확인 방법을 쓰고, 그 빈틈을 PASS 기준에서 빼지 않는다.
7. “제대로 처리”, “적절히 구현”, “전부 최적화”처럼 판단이 남는 문장을 제거한다.
8. 요구→카드→테스트가 연결되는지 자체 대조한다. 이 대조를 모델 성공률 평가라고 부르지 않는다.

출력 순서:
ID와 기존 parent_id
목표(한 문장) / 제외 범위
읽을 파일·기획 절
쓰기 허용 파일(정확한 경로; 신규는 신규라고 표기)
선행 작업·필요 승인·확인할 실제 상태
입력→출력 인터페이스
5~8개 실행 순서
수용 조건 표: ID | Given | When | Then | 검사 방법
필수 회귀 검사
막힘·에스컬레이션 조건
인계할 증거와 다음 한 작업

제약:
- 카드가 원하는 출력을 만들어내도록 기대 결과를 수정하지 않는다.
- 숨겨진 chain-of-thought를 요구하지 않는다. 짧은 결정 이유·근거·실행 결과만 요구한다.
- 성공/실패 예시는 EXAMPLE로 구분한다. 예시 로그를 실행 증거에 복사하지 않는다.
- 제한 입력만 전달하되 핵심 규칙·최신 코드·필수 테스트는 생략하지 않는다.
- 기획/코드 충돌이 연구 규칙·보안·공개 정책을 바꾸면 결정자에게 그 쟁점만 보낸다.
- 프로젝트 전체 원장이나 AGENTS를 자동 덮어쓰지 않는다.
```

출력을 채택하려면 기존 catalog의 파일·심벌·의존성 충돌을 검토하고, 소유자/승인을 확인한다. 상위 기획을 바꾸어야 하는 요청이면 먼저 기획 수정안을 만들며 실행 카드로 몰래 정책을 바꾸지 않는다.
