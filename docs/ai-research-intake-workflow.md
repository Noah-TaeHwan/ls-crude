# AI 연구 접수 워크프로세스 — 아이디어와 데이터 접근 확인

**AI에게 한 번에 최대 3개의 아이디어를 맡기고, 실제 데이터를 구할 수 있는지와 무엇을 측정하는지 확인한 기록을 GitHub PR로 남긴다.** 성공한 후보뿐 아니라 자료 부족·차단·측정 불일치도 같은 이력에 보존한다.

이 단계의 끝은 데이터 접근·샘플 확인이다. 지수 조합, 회귀분석, WTI 가격 검정, 웹사이트 구현은 다음 작업으로 분리한다. 이 가이드는 반복 실행용 문서이며 스케줄러나 자동 수집 서비스를 설치하지 않는다.

## 2. 한 번의 작업 단위

```text
요청자가 범위·담당·GitHub 전달 방식을 지정
    ↓
AI가 현재 브랜치·기존 연구·중복 확인
    ↓
실제 아이디어를 카드·원장에 등록하거나 기존 후보를 이어서 조사
    ↓
원 제공자·접근법·허용 범위 확인
    ↓
허용된 작은 샘플 취득 → 단위·지역·시각·측정 적합성 확인
    ↓
가능 / 대기 / 접근 차단 / 오류 / 측정 불일치의 근거 기록
    ↓
검증 → 범위 내 파일만 커밋 → 피처 브랜치 push → PR
    ↓
사람이 근거를 읽고 다음 단계·재개·종료 결정
```

자료를 못 구한 경우도 조사 결과다. 단, ‘검색했지만 찾지 못함’과 ‘제공자가 미제공을 명시함’은 구분한다. 단순한 API 오류 하나를 데이터의 영구 부재로 해석하지 않는다.

### GitHub에 남길 것

| 기록 | 경로 / 내용 |
| --- | --- |
| 후보 상세와 이력 | `research/candidates/<candidate_id>.md` — 가설, 실제 관측, 출처, 접근 시도, 다음 행동 |
| 후보 요약 | `research/candidates/ledger.csv` — 카드와 같은 변경에서 갱신 |
| 출처 정보 | `research/gathering/sources/REGISTRY.md` — 기존 출처는 재사용, 새 출처만 추가 |
| 실행별 노트 | `research/gathering/notes/YYYY-MM-DD-<slug>-<run>.md` — 조사 범위, 시도·실패·검토, 후보 링크 |
| 원본 취득 영수증 | `research/gathering/raw/<candidate_id>/<UTC수집시각>/README.md` — URL, 파일명, SHA-256, 행 수·기간, 실제 명령, 재취득 방법 |
| 수집 보조 코드가 필요할 때 | `research/notebooks/<candidate_id>/` — 기존 코드 재사용 우선, 작은 수집·검사 코드만 |

**원본 CSV·ZIP·영상·응답 덤프는 기존 gitignored raw 경로에 보존하고 커밋하지 않는다.** GitHub에는 원문 대신 요약·근거·재현 방법을 남긴다. 공개 README와 명령에도 키·토큰·서명 URL·개인정보를 넣지 않는다. 자료를 실제로 받지 않았다면 hash나 행 수를 만들지 않는다.

노트의 `<run>`은 같은 날 같은 주제를 반복할 때 파일명이 겹치지 않게 고른다. 기존 노트·원본을 덮어쓰지 않고 후보 카드의 변경 이력에 새 노트를 연결한다. 조사 결과는 새 폴더로 상태별 복제하지 않는다.

## 3. 복사해서 AI에게 보낼 기본 프롬프트

아래 코드 블록 전체를 복사한다. 기본 담당은 요청자인 오태환이며 성찬이 실행할 때는 손성찬으로 바꾼다. 담당은 후속 작업의 기록 책임자이고 사람 검토 완료를 의미하지 않는다.

```text
LS CRUDE에서 ‘가설(아이디어) → 데이터 접근·샘플 확인’만 수행해줘.

[작업 설정]
- 저장소: Noah-TaeHwan/ls-crude. 현재 로컬 checkout을 확인해서 사용.
- 지역·현상: 쿠싱의 원유 저장·운송과 연결될 수 있는 최신 활동의 흔적.
- 지정 아이디어/기존 후보 ID: 없음. 기존 이력과 중복하지 않는 후보를 직접 제안.
- 후보 수: 최대 3개. 숫자를 채우려고 아이디어를 만들지 말 것.
- 기록 담당: 오태환.
- GitHub 전달: PR까지. 이 요청은 이번 작업 파일의 commit·push·PR 생성을 승인한다.
  main 직접 commit·push, merge, deploy는 요청하지 않는다.

[먼저 확인]
1. AGENTS.md와 관련 스킬, research/INTAKE.md, docs/recording-standard.md,
   docs/testing-protocol.md, docs/ai-research-intake-workflow.md를 읽어라.
   오래된 crypto×news 전용 문서 대신 현 INTAKE의 활동 proxy 규약을 따른다.
2. git status와 원격 main을 확인한다. 기존 변경과 다른 사람의 작업을 보존한다.
   최신 원격 main에 기반한 research/<짧은주제> 피처 브랜치에서 작업한다.
   현재 checkout을 안전하게 전환할 수 없다면 격리 worktree를 사용한다.
3. research/candidates/ledger.csv, 카드, research/factors/README.md와 관련 노트를 먼저 찾아
   동일 관측·가설·출처의 과거 실패나 보류를 확인한다.
   지정 아이디어가 기존 후보라면 재개 조건을 확인해 같은 기록을 잇는다.
   같은 후보를 이름만 바꿔 새 발견으로 등록하지 않는다.
   옛 factors에만 있는 후보는 legacy_ref와 기존 판정을 연결하고,
   현 규약상 신규 카드가 필요하더라도 새로운 발견으로 세지 않는다.

[조사]
4. 각 아이디어를 한 문장으로 쓴다:
   ‘우리는 쿠싱의 ___가 달라졌는지 알고 싶고, 그 흔적으로 ___를 관측한다.’
   실제 측정값, WTI까지의 연결 가설, 대체 설명 하나를 구분한다.
   모텔 밝기를 투숙객 수로, 도시권 자료를 특정 모텔 자료로 바꾸어 부르지 않는다.
   다른 지역 자료는 쿠싱 현지 관측과 분리하고 연결 근거를 적는다.
5. 새 후보는 실제 등록 전에 최신 원장·카드와 ID 중복을 다시 확인한다.
   ALT-YYYYMMDD-NN은 현 기록 규약의 등록일 KST·일별 빈 번호 규칙을 따른다.
   템플릿 필드를 유지하고 카드와 CSV를 함께 기록한다.
6. 원 제공자·공식 API·파일을 우선 조사한다. 링크 발견에 그치지 말고,
   허용 범위 안에서 작은 실제 샘플을 받아 무엇이 들어 있는지 확인한다.
   다운로드 전에 샘플 대상·기간·크기와 중단 조건을 정한다.
   계정·비용·허가가 필요하면 우회하지 않고 조건을 기록한다.
   제공자 제한과 Retry-After를 지키며 같은 실패를 끝없이 반복하지 않는다.
7. 받은 샘플의 단위·지역·해상도·시간 범위·행 수·결측·중복을 확인한다.
   관측일, 최초 공개일, 수집일과 갱신 주기를 구분한다.
   ‘오늘 받은 파일’과 ‘오늘의 활동’을 혼동하지 않는다.
   최신성·역사 빈티지·지속 취득·재배포를 확인하지 못하면 미확인으로 적는다.
   최근 자료의 접근 시연을 과거 검증이나 미열람 OOS로 부르지 않는다.
8. 샘플이 아이디어의 현상을 관측하는 데 충분한지 판단한다.
   불충분하면 측정 범위를 낮추거나 보류/종료한다.
   자료 부재·접근 차단은 가설이 거짓이라는 증거가 아니다.

[기록과 상태]
9. 카드·원장·출처 레지스트리·실행별 노트에 근거를 연결한다.
   원본은 research/gathering/raw/<id>/<UTC수집시각>/에 불변 보존하고 공개 README 영수증을 작성한다.
   실제 받은 파일에만 hash·행 수·기간을 기록한다. 원문 덤프는 Git에 넣지 않는다.
10. 신규 후보는 현재 규약의 상태를 사용한다:
    - 대기: NOT_STARTED / NOT_RUN / PARK.
    - 접근·권리·역사 조건 미충족: BLOCKED / NOT_RUN / PARK.
    - 실제 수집 오류: FAILED / NOT_RUN / PARK.
    - 샘플만 확보, 필요 범위 수집 미완료: COLLECTING / NOT_RUN.
    - 필요한 원본 수집과 영수증을 완료한 경우만 COLLECTED.
    collection_status와 evidence_level과 decision을 별도로 판단한다.
    출처 접근·샘플 확인 단계는 E0 또는 E1이며,
    샘플을 받았다는 이유만으로 지수 구성 단계인 E2로 올리지 않는다.
    샘플의 파싱·품질 검사는 이 단계의 WTI 관계 검정 RUN을 뜻하지 않는다.
    KEEP은 다음 단계의 자료 구성·시각화 투입이 정당화될 때만 쓰고,
    무엇이 충족됐고 무엇이 남았는지 적는다. 불확실하면 PARK.
    KILL은 현 측정 방식의 불일치 등 구체적 종료 근거가 있을 때만 쓴다.
    이력은 삭제하지 않는다.
    기존 후보 재개 시에는 과거 RUN·증거 수준·결과를 초기화하지 않는다.
    이번 실행의 미검정과 추가 확보 범위는 새 노트에 구분해 적고,
    카드의 현재 상태를 바꿀 때만 이전 상태·변경 근거·남은 제한을 기록한다.
11. 다음 행동은 후보마다 하나만 쓰고 담당·재검토일을 제안으로 명시한다.
    AI 검토자와 사람 검토자를 구분하고 미검토를 검토 완료로 채우지 않는다.

[이번에 하지 않을 것]
- 상관·회귀·ML/DL·백테스트·가격 데이터 수집·OOS 열람.
- 복합 인덱스·알림·차트·앱·대시보드 변경, docs/experiments 승격.
- 개별 선박·개인·예약·결제 추적, Investing.com 스크래핑.
- 성능·행 수·출처·허가·실행 성공의 추정 또는 날조.

[검증과 GitHub 전달]
12. docs/recording-standard.md의 원장 구조 검사를 실행하고,
    이번에 바꾼 카드와 CSV의 필드·상태·경로를 직접 대조한다.
    실패하면 이번 변경 원인인지 기존 문제인지 구분하고,
    기존 문제는 근거를 남기되 무관한 수정으로 범위를 넓히지 않는다.
    내부 링크·실제 원본/영수증·재취득 절차·변경 diff를 확인한다.
    코드가 추가됐다면 필요한 작은 검사를 실제 실행한다.
13. GitHub 전달 설정이 PR까지라면 이번 작업 파일만 명시적으로 stage한다.
    staged diff를 검토해 덤프·시크릿·타인 변경이 없는지 확인한 뒤
    Conventional Commit + 한국어 본문으로 commit하고 feature branch를 push한다.
    gh로 main 대상 PR을 만든다. merge·deploy·force push는 하지 않는다.
    최신 main에 같은 후보/ID가 생겼으면 내용·ID를 조정하고 다시 검사한다.
    CI 결과를 확인하고 미완료·실패를 숨기지 않는다.
    설정이 로컬 기록만이면 commit·push·PR은 하지 않는다.
14. 최종 답변은 후보별 ‘아이디어 / 실제 측정값 / 접근 결과 / 확보 범위 /
    상태·판정 / 미확인 사항 / 다음 행동’ 표와 파일·PR 링크로 마친다.
    원본이 로컬에만 있거나 GitHub 접근이 실패하면 그 사실과 남은 작업을 적는다.
    구조 검사 통과를 데이터 유효성·예측력 검증이라고 쓰지 않는다.
```

## 4. 같은 프롬프트를 바꾸어 쓰는 방법

별도 프롬프트 시스템을 만들지 않고 위 설정만 바꾼다.

| 요청 | 바꿀 설정 |
| --- | --- |
| 새 아이디어 탐색 | 지정 아이디어 `없음`, 범위와 최대 후보 수 지정 |
| 모텔 불빛 하나 확인 | 지정 아이디어에 ‘쿠싱 모텔 주변 밝기 변화’를 적고 후보 수 `1`; 기존 091 이력을 먼저 확인 |
| 보류 후보 재개 | 지정 아이디어에 기존 후보 ID와 확인할 재개 조건 입력 |
| 성찬 담당 실행 | 기록 담당을 `손성찬`으로 변경 |
| 올리기 전 로컬 검토만 | GitHub 전달을 `로컬 기록만`으로 변경 |

기본 프롬프트의 `PR까지`는 복사해 요청하는 해당 실행의 게시 승인이다. 이전 실행의 승인을 모든 향후 실행에 임의 적용하지 않는다. PR 작성은 연구 기록 전달이며 외부 사람에게 별도 메시지·이메일을 보내는 요청은 아니다.

## 5. 두 사람이 동시에 쓸 때

- 서로 다른 후보를 나눠 맡고 각자 피처 브랜치·checkout을 사용한다.
- 기존 후보의 같은 카드는 한 사람이 책임진다. 카드·원장·출처 표 같은 공유 파일을 동시에 직접 수정하지 않는다.
- PR 통합 담당이 최신 main과 열린 PR의 후보 ID·중복을 확인하고 충돌을 해소한다. ID 충돌을 피하려고 기존 연구를 덮어쓰거나 삭제하지 않는다.
- 요청자와 검토자는 PR에서 출처·실제 샘플 여부·측정 의미·남은 조건을 확인한다. 재실행하지 않았다면 사람 재현은 미검증으로 남긴다.
- 다음 단계는 ‘수집·시각화 진행’, ‘조건이 생기면 재개’, ‘현 방식 종료’ 중 하나로 정한다. KEEP이 자동 구현·배포 승인이 되지는 않는다.

## 6. 기록이 제대로 남았는지 보는 기준

| 상황 | 올바른 기록 | 잘못된 기록 |
| --- | --- | --- |
| 소개 페이지만 찾음 | 출처 발견, 원본 미수집 | COLLECTED |
| 403 또는 계정 필요 | 시각·접근 경로·차단 조건 | ‘데이터가 세상에 없음’ |
| 도시 야간광만 받음 | 도시권 밝기, 모텔 판독 부적합 가능성 | 모텔 객실점유율 확보 |
| 샘플 1개만 받음 | 실제 확보 범위와 남은 수집 | 장기 패널 완성·E2 |
| 같은 후보를 다시 조사 | 같은 이력에 새 노트·변경 이유 | 이름만 바꾼 새 발견 |
| 데이터 접근 성공 | 다음 관측 단계에 필요한 조건 판단 | WTI 예측력 통과 |
| 다른 작업이 main에 추가됨 | 현재 자료·판정을 재확인 | 이전 대화만 믿고 중복 등록 |

이 표는 프롬프트의 검토 기준이다. 이 가이드 작성 자체로 해당 사례의 조사나 샘플 취득을 실행한 것은 아니다.

**한 번의 완료:** 성공·실패와 무관하게 실제 시도와 근거, 측정 범위, 다음 행동을 찾을 수 있고, 요청한 전달 방식에 맞춰 파일 또는 GitHub PR이 남아 있다. GitHub에 저장한 이력이 main에 반영되는 것은 별도 PR 검토·병합 단계다.
