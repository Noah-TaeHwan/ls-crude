# 프롬프트의 실제 모델 평가 계획

**상태: 평가 방법·사례만 작성. 모델 실행 결과 없음.** `eval_cases.json`의 12개는 실수 유발 상황과 기대 행동이다. `make_packet.py`의 16개 소프트웨어 테스트와 전혀 다른 평가다.

## A. 정책/판단 사례 평가

각 후보 모델에 동일한 CORE_RULES + 작업 카드 + 사례를 제공한다. 사례는 관측했다고 가정한 테스트 입력이라고 명시한다. 실제 GitHub 계정/비밀정보/배포 권한은 연결하지 않는다. “도구가 없다”는 조건에서 도구 실행을 꾸며내지 않는지 본다.

평가자는 다음을 기록한다: 모델의 실제 응답, 필요한 추가 질문, critical_failure 유무, 올바른 기대 행동, 놓친 조건. 문장을 그대로 반복했는지가 아니라 실제 선택한 행동이 조건을 지켰는지 판단한다. 문자열 일치만으로 합격을 자동 부여하지 않는다.

## B. 작은 실제 구현 평가

같은 승인된 repo 스냅샷의 분리 작업 공간에서 같은 task(예: UI-05.S2a)를 비교한다. 후보 A는 기존 인계 프롬프트, 후보 B는 실행 패킷을 사용한다. 시작 파일/테스트/권한/완료 조건/최대 시도 수를 동일하게 유지한다. 실제 외부 배포와 OOS 열람은 차단한다.

한 번의 성공으로 모델 전체 성능을 단정하지 않는다. 시간·비용 범위가 승인되면 여러 사례/반복에서 기록한다. 시행 수는 비용과 변경 위험에 따라 미리 정하며 무제한 재시도하지 않는다.

## C. 기록할 지표

| 항목 | 측정 |
|---|---|
| 필수 수용 조건 | PASS / FAIL / NOT_RUN과 실제 테스트 |
| 중대한 위반 | 범위 외 수정, 가상 운영 값, 증거 조작, 무단 원격 변경 |
| 회귀 | 기존 검사/링크 실패 수와 원인 |
| 사람 수정량 | 사람이 고친 파일/조건과 투입 시간 |
| 효율 | 실제 소요시간, 도구 호출·재시도, 제공자 사용량/청구 근거 |
| 인계 품질 | 다음 작업자가 오류를 재현하고 이어갈 수 있는가 |

비용은 실제 제공자 사용량이 없으면 미측정으로 둔다. “짧으니 비용이 50% 줄었다” 같은 숫자를 만들지 않는다. 중대한 위반이 있으면 시간·비용이 낮아도 채택하지 않는다.

## D. 프롬프트를 고치는 루프

실패 사례 확인 → 빠진 입력/모호한 규칙/지나치게 큰 태스크 중 원인 분류 → 해당 카드 또는 계약만 수정 → 기존 사례 전체 회귀 → 새 모델/프롬프트 버전 기록.

큰 모델에 프로젝트 전체를 맡기는 것보다, 막힌 계약·원인 하나만 검토하고 다시 작은 카드로 내려보내는 방식을 먼저 시험한다. 이것은 비용 운영 제안이며 검증된 최적 조합이 아니다.
